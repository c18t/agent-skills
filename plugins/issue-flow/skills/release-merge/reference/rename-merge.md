# リネームを含む PR を統合するとき

`release-merge` スキルの手順 2・6・8 から参照する。
ディレクトリ改名を含む PR と、改名前のパスに新規ファイルを足す PR を統合すると起きる罠と、その対処。

## 新規ファイルが旧ディレクトリに着地する

次の 2 本を統合する場面を考える。

- **PR A** … `packages/old-name/` → `packages/new-name/` へディレクトリを改名する
- **PR B** … `packages/old-name/docs/` に新規ファイルを 2 つ追加する（A の改名を知らない）

A → B の順で merge すると、こうなる。

```text
CONFLICT (modify/delete): packages/old-name/package.json deleted in HEAD and modified in ...
A  packages/old-name/docs/guide.md
A  packages/old-name/docs/reference.md
```

**新規ファイルの 2 つは衝突として報告されない。** git がリネームを追跡できるのはマージベースに
存在したファイルだけで、B が足した 2 ファイルはマージベースに無いため対応付けができない。
結果として**削除したはずの `packages/old-name/` が復活し、そこに置かれる。**

## 検証が全部通ってしまう

この状態でも手順 7 の検証は通ることが多い。

- Markdown / コードの lint … 通る（ファイル単体としては妥当）
- マニフェストやパッケージ定義の検証 … 通る（参照先の `new-name` 側は正しい）
- 参照の実在確認 … 通る（`old-name` を参照するものが無いだけで、存在自体は咎められない）

**孤立したディレクトリを検出する仕組みは普通は無い。** 親ディレクトリを目で見るか、
`git status` の `A` を読むまで気づかない。

## 対処

- **リネームを含む PR を先にマージする**（手順 2 のマージ順）。構成を確定させてから
  新規ファイルを載せれば、移動が 1 回で済む
- リネームを含む PR が対象にあるときは、**各マージ後に `git status` の `A` を確認する**（手順 6）。
  新規ファイルが旧パスに着地していないか
- 着地していたら `git mv` で正しい場所へ移し、空になった旧ディレクトリを消す。
  衝突解消と同じコミットに含め、手順 9 の「競合解消」欄に記録する
- 統合後に対象ディレクトリの親（上の例なら `ls packages/`）を**目で見る**（手順 8）

## 旧名の残留を grep する

リネームを含む統合では、lint が全部通ったあとにも旧名が残る。典型的には次の 2 種類。

- パッケージ定義や README の description が、改名前の構成を数えたまま
  （「2 モジュール」など。増減のたびに古くなる書き方なので、数えない表現に改める）
- 文書の中の呼び出し文字列・相互参照・例示に残った旧名

```bash
grep -rn "old-name" packages/ README.md
```

⚠️ **置換先は意味に応じて変わる。** 機械置換すると壊れる箇所がある。

| 出現箇所 | 扱い |
| --- | --- |
| 呼び出し文字列、相互参照、パス | 新名へ置換する |
| ブランチ名・PR タイトル・コミットメッセージの**例示** | 例示が成り立つ名前に個別に直す（機械置換すると例が壊れる） |
| 過去の経緯の説明（「旧名 X から改名した」など） | そのまま残す |

1 件ずつ意味を見て判断する。`sed` で一括置換しない。
