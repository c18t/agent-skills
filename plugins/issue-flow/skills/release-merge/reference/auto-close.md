# PR と issue の自動クローズ

`release-merge` スキルの手順 12 から参照する。**ここが一番間違えやすい。**

PR と issue で条件が違い、さらに issue のほうは**発火源が 2 つある。**

## 条件

| 対象 | 条件 |
| --- | --- |
| **PR 自身** | head コミットが**その PR 自身の base** へマージされること |
| **issue**（PR 本文の `resolves:`） | **その PR が**デフォルトブランチへマージされること |
| **issue**（コミットメッセージの `resolves:`） | **そのコミットが**デフォルトブランチへ到達すること |

⚠️ **PR 本文とコミットメッセージは別経路。** 同じ `resolves: #123` でも、どちらに書いたかで
発火条件が変わる。ここを取り違えると issue が閉じない。

## base を張り替えると発火しなくなる

**PR のクローズ条件は「自分の base へマージされること」であって、main への到達ではない。**
`gh pr edit --base` で base を release ブランチへ向けた瞬間から、その PR は release を見る。
release へマージした時点で **Merged になる。まだ main には何も入っていないのに。**

そして **base を張り替えた PR の本文に書いた `resolves:` は永久に発火しない。**
PR 本文の経路はデフォルトブランチへのマージが条件だが、その PR は release へのマージで
既に Merged 済み。**処理済みの PR は、あとから main に入っても再評価されない。**

実際に、base を release へ張り替えた 2 本の PR で挙動が割れたことがある。

- **片方は issue が閉じた** … コミットメッセージ本体にも `resolves:` が入っていたため、
  そのコミットが main に到達した時点で**コミットメッセージ側の経路が**発火した
- **もう片方は閉じなかった** … `resolves:` が PR 本文にしかなかった

つまり閉じたほうは、たまたまコミットメッセージ側にも書いてあったからで、運でしかない。

## 対策

どちらでもよい。両方やってもよい。

- **base を張り替えない**（スキル手順 6 の既定）… PR 本文の `resolves:` がそのまま効く
- **`resolves:` をコミットメッセージ本体にも書く** … 経路が二重になり、
  base を張り替えても片方は生き残る

## マージ方法は両方向とも merge commit

**PR → release も、release → main も merge commit にする。**
squash すると head SHA が変わり、PR が「head が base に到達した」と判定できなくなる。

リリース PR テンプレートの「マージ方法」の記載は release → main を指したものだが、
**PR → release も同じ理由で merge commit が要る。**

## 閉じ損ねた issue の手当て

```bash
gh issue close <番号> --comment "..."
```

**そのとき、どのコミットで対応したかをコメントに残す。** 黙って閉じない。
自動クローズが発火していれば「どの PR で閉じたか」が履歴に残るが、手動クローズは
その情報を持たないため、あとから追跡できるのはコメントだけになる。
