# issue を起草して作る

引数は作りたい issue のテーマ（自由文）。省略されたら何の issue かをユーザーに聞く。

テーマを受け取ったらリポジトリの状況を調べ、タイトル・本文・ラベルを組み立てて、
**チャットに全文を書き出してユーザーのレビューを待つ。** 承認されたら `gh issue create` で作り、
作った issue に着手するための導線を示して終わる。

ユーザーの承認を取るのは 1 箇所（手順 6 の本文レビュー）。それ以外は続けて進めてよい。

このスキルは issue を**作る**側。作った issue に着手するのは `issue-work` スキルの担当で、
このスキルからは呼び出さない（手順 8）。

## 手順

### 1. リポジトリと既存 issue を確認する

```bash
gh repo view --json nameWithOwner,description
gh issue list --limit 30 --state all
```

**既存 issue を見るのは重複を避けるため。** 同じ話題が既にあれば、新規作成ではなく
既存 issue へのコメント追記で足りることがある。近いものが見つかったら、
新しく作るか既存に足すかをユーザーに聞く。

`gh` が未認証だとここで落ちる。その場合は `gh auth status` の実行を案内して**止まる**。
**認証を代行しない。**

### 2. issue テンプレートの有無を確認する

```bash
ls .github/ISSUE_TEMPLATE/ 2>/dev/null
```

| 状態 | やること |
| --- | --- |
| ある | その中から適切なテンプレートを読み、見出しをそのまま使う |
| 無い | 手順 5 の既定形（背景 / やること / 影響範囲 / 補足）を使う |

テンプレートがある場合は**リポジトリ側の見出しを優先する。** 既定形を上書きしない。

### 3. ラベルを決める

```bash
gh label list
```

**必ず実在するラベルを確認してから選ぶ。** 存在しないラベルを `--label` に渡すと
`gh issue create` が失敗する（手順 7 で作成そのものが落ちる）。

| 内容 | ラベル |
| --- | --- |
| 不具合・壊れている | `bug` |
| 規約の変更・機能追加 | `enhancement` |
| ドキュメントの追加・改善 | `documentation` |

この 3 つに収まらない、または複数に当てはまって決めきれないときは**ユーザーに聞く。**
リポジトリによってはラベルが未整備なこともある。その場合はラベル無しで作ってよい。

### 4. タイトルを決める

**英語。** `<対象>: <英文>` の形にする。`<対象>` は変更が入るプラグイン名・
コンポーネント名・ファイル名など、どこの話かが分かる語。

```text
issue-flow: follow Conventional Branch for branch naming
notion-writeback: resolve python3 launcher on Windows
```

コミットメッセージと同じ流儀で、description は小文字始まり・命令形・末尾ピリオドなし。

### 5. 本文を起草する

**日本語。** テンプレートが無い場合の既定形は次の 4 つ。

| 見出し | 書くこと |
| --- | --- |
| **背景** | 現状どうなっていて何が問題か。なぜ今これを挙げるのか |
| **やること** | 具体的な変更。**判断が要るものは根拠も書く** |
| **影響範囲** | 破壊的変更かどうか、version をどう上げるか、他への波及 |
| **補足** | 分割元の PR、参考リンク、検証済みの事実 |

**「やること」に判断の根拠を残すのがこのスキルの主目的。** なぜその命名なのか、
なぜその方式を選んだのかを書いておくと、あとで着手するときに同じ検討をやり直さずに済む。
「〜する」だけを並べて根拠を落とさない。

🔴 **採番前の番号を本文に書かない。** issue や PR の番号は作成後に GitHub が採番する。
書いた時点では自分の番号は分からず、書きかけると存在しない番号を参照することになる。
相互参照が必要なら**作成後に** `gh issue edit <番号> --body-file <ファイル>` で追記する。

既に採番済みの番号（先行する issue や、マージ済みの PR）を参照するのは問題ない。
`gh issue list` / `gh pr list` で実在を確かめてから書く。

### 6. 本文をチャットに書き出してレビューを待つ

タイトル・ラベル・本文の全文をチャットに出す。そのうえでユーザーのレビューを待つ。

**この手順では `gh issue create` を実行しない。** 承認されるまで作成しない。
issue の作成は外向きの操作で、作ったあとの取り消しはクローズしかできないため。

### 7. 承認されたら作成する

```bash
gh issue create --title "<タイトル>" --body-file <本文ファイル> --label <ラベル>
```

🔴 **`--body` ではなく `--body-file` を使う。** 日本語の長文をシェルの引数に直接渡すと、
引用符・改行・バッククォートで壊れる。本文はファイルに書いてから渡す。

ラベルを複数付けるときは `--label a --label b` のように繰り返す。

作成に失敗したら**そのまま再実行しない。** ラベル名の誤り（手順 3 を飛ばした場合）か
未認証（手順 1 を飛ばした場合）が原因のことが多いので、エラーメッセージを読んで原因を特定する。

### 8. URL を報告し、着手の導線を示す

作成された issue の URL と番号を伝える。そのうえで、着手するためのコマンドを提示して終わる。

```text
/issue-flow:issue-work <番号>
```

**ここで issue-work を自分で呼び出さない。** 起票と着手は別の判断なので、
続けて着手するかどうかはユーザーが決める。

手順 5 で相互参照を保留していた場合は、ここで `gh issue edit <番号> --body-file <ファイル>` を
実行して追記する。

## 落ちる原因（既知）

- **採番前の番号を本文に書く** … issue / PR の番号は作成後に決まる。書いた時点では未定なので、
  相互参照は手順 8 で `gh issue edit` を使って追記する
- **存在しないラベルを指定する** … `gh issue create --label` が失敗して作成ごと落ちる。
  手順 3 の `gh label list` を飛ばさない。リポジトリごとにラベルは違う
- **`--body` に日本語の長文を直接渡す** … 引用符・改行・バッククォートでシェルが壊れる。
  `--body-file` を使う
- **`gh` が未認証** … 手順 1 で落ちる。`gh auth status` を案内する。**認証を代行しない**
- **既存 issue と重複させる** … 手順 1 の `gh issue list` を飛ばすと起きる。
  同じ話題が既にあればコメント追記で足りることがある
- **リポジトリのテンプレートを無視して既定形で書く** … `.github/ISSUE_TEMPLATE/` がある
  リポジトリでは、そちらの見出しが優先される。手順 2 で確認する
- **本文を書き出さずに作ってしまう** … 手順 6 の承認ゲートを飛ばさない。
  作成後の取り消しはクローズしかできない
