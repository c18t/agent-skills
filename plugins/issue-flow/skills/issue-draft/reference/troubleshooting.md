# issue-draft で落ちる原因（既知）

`issue-draft` スキルの各手順から参照する。手順番号は `SKILL.md` のもの。

## 採番前の番号を本文に書く

issue / PR の番号は作成後に GitHub が採番する。書いた時点では自分の番号は分からず、
書きかけると存在しない番号を参照することになる。

相互参照が必要なら**作成後に** `gh issue edit <番号> --body-file <ファイル>` で追記する（手順 8）。
既に採番済みの番号（先行する issue や、マージ済みの PR）を参照するのは問題ない。
`gh issue list` / `gh pr list` で実在を確かめてから書く。

## 存在しないラベルを指定する

`gh issue create --label` が失敗して作成ごと落ちる。手順 3 の `gh label list` を飛ばさない。
リポジトリごとにラベルは違う。ラベルが未整備なリポジトリではラベル無しで作ってよい。

## `--body` に日本語の長文を直接渡す

引用符・改行・バッククォートでシェルが壊れる。本文はファイルに書いて `--body-file` で渡す（手順 7）。

## `gh` が未認証

手順 1 の `gh repo view` で落ちる。`gh auth status` の実行を案内して**止まる。認証を代行しない。**

GitHub MCP のツールが使えるならそちらの経路で続けられる
（[../../issue-work/reference/github-mcp.md](../../issue-work/reference/github-mcp.md) の判定順）。
`gh` 自体が無い環境（Cowork など）では `gh auth status` の案内は解決策にならないので、
GitHub MCP サーバーのセットアップを案内する（プラグイン README の前提）。MCP も無ければ止まる。

## 既存 issue と重複させる

手順 1 の `gh issue list` を飛ばすと起きる。同じ話題が既にあれば、新規作成ではなく
既存 issue へのコメント追記で足りることがある。近いものが見つかったら、
新しく作るか既存に足すかをユーザーに聞く。

## リポジトリのテンプレートを無視して既定形で書く

`.github/ISSUE_TEMPLATE/` があるリポジトリでは、そちらの見出しが優先される。
同梱の [templates/issue.md](../templates/issue.md) はリポジトリ側に無いときだけ使う（手順 2）。

## 本文を書き出さずに作ってしまう

手順 6 の承認ゲートを飛ばさない。issue の作成は外向きの操作で、
作ったあとの取り消しはクローズしかできない。

## 作成に失敗したあと、そのまま再実行する

ラベル名の誤り（手順 3 を飛ばした場合）か未認証（手順 1 を飛ばした場合）が原因のことが多い。
エラーメッセージを読んで原因を特定してから再実行する。
