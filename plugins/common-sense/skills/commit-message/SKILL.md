# コミットメッセージを書く

コミットは、1 年後に履歴や `git blame` を読む人へ「なぜ今この変更が必要で、なぜこの形にしたか」を
伝える。いまのセッションの作業報告にはしない。

## 1. リポジトリの宛先表を確認する

リポジトリの `AGENTS.md` に、コミット時の情報をどこへ残すかを定めた宛先表や同等の規約があれば、
その表を使う。無ければ次の既定を使う。

| 内容 | 宛先 |
| --- | --- |
| diff から読める変更内容 | 書かない |
| コードがその形である理由 | ソースコメント |
| 作業経緯、試して採用しなかった案 | PR 本文の候補 |
| 未決事項、後続で必要な作業 | issue コメントの候補 |
| なぜ今この変更が必要か、なぜこの形を選んだか | コミット本文 |

宛先表は情報の分類にだけ使う。外部の issue、PR、プロジェクト文書は自動更新しない。

## 2. diff から分類する

下書きや会話の要約ではなく、コミット対象の diff を読む。ステージ済みの変更があれば
`git diff --cached` を優先し、ユーザーが範囲を指定した場合はその diff を使う。

説明したくなった各項目について、diff だけで読み取れるかを最初に判定する。読める項目は削り、
残った項目を宛先表へ振り分ける。コードの理由が将来の変更時にも必要なら、メッセージに逃がさず
ソースコメントを追加または修正してから diff を見直す。

PR 本文、issue コメント、その他のプロジェクト文書へ向かう項目は、その場で書き込んだり、
最終的な宛先を決めたりしない。「候補」としてユーザーに提示する。

## 3. 粒度を確認する

コミット本文に残る独立した why が 2 つ以上なら、コミット分割の候補として提示する。
分割するかはユーザーが決める。why が複数でも不可分なら、その関係が分かるメッセージにする。

## 4. 一度に提示する

1 コミットにつき、必要な内容を 1 回にまとめて提示する。

- コミットメッセージ案
- 追加または修正したソースコメント（ある場合）
- PR 本文、issue コメント、その他の文書へ回す候補と、その候補先
- コミット分割の候補（ある場合）

候補が無い欄は省略する。項目ごとに確認を挟まない。

コミットメッセージの書式はリポジトリの規約に従う。規約が無ければ、件名は変更を端的に表し、
本文は diff の言い換えを避けて、残った why だけを書く。
